JARVIS — CANONICAL ARCHITECTURE BLUEPRINT
=========================================

STATUS:
LOCKED ARCHITECTURE
This document is the single source of truth for JARVIS architecture.

============================================================
0. CORE PRINCIPLE
============================================================

JARVIS is a living cognitive system.

It must NOT be designed as:

Input → LLM → Output

Instead:

Input
 ↓
Perception
 ↓
Cognition
 ↓
Cognitive Router
 ↓
Native / Hybrid / LLM Fallback
 ↓
Brain Decision
 ↓
Action / Response
 ↓
Experience
 ↓
Self-Evaluation
 ↓
Learning / Knowledge
 ↓
Evolution

Learning and evolution are controlled boundaries.
No component may silently bypass another boundary.

============================================================
2. PERCEPTION
============================================================

USER INPUT
    ↓
Perception

Responsibilities:

    ├── Normalization
    ├── Language Detection
    ├── Intent Extraction
    ├── Entity Extraction
    └── Structured Perception Output

Perception does NOT:

    ├── execute actions
    ├── learn skills
    ├── modify knowledge directly
    └── make final brain decisions

============================================================
3. COGNITION
============================================================

Perception Output
    ↓
Cognition

Cognition provides the current internal context:

    ├── Memory
    ├── Knowledge
    ├── Goals
    ├── State
    ├── Capabilities
    └── Experience

Cognition prepares evidence/context.

It does NOT independently choose the execution path.

That responsibility belongs to the Cognitive Router.

============================================================
4. COGNITIVE ROUTER
============================================================

Perception + Cognition
          ↓
   Cognitive Router

Router decides:

    ├── NATIVE
    ├── HYBRID
    └── LLM FALLBACK

NATIVE:
Known structured intent + sufficient local capability + sufficient evidence.

HYBRID:
Native deterministic work → native result → LLM interpretation/synthesis when required.

LLM FALLBACK:
Used when native cognition lacks sufficient evidence or capability.

IMPORTANT:
LLM is a fallback/reasoning component.
LLM is NOT the owner of JARVIS architecture.

============================================================
5. BRAIN DECISION
============================================================

Cognitive Router result → Brain

Brain commits the selected cognitive result into a structured decision containing:

    ├── action
    ├── response
    ├── route
    ├── result/status
    └── relevant execution context

============================================================
6. ACTION / RESPONSE
============================================================

Brain Decision → Action / Response

Both SUCCESS/COMPLETED and FAILURE become Experience.
No meaningful execution result is silently discarded.

============================================================
7. EXPERIENCE
============================================================

Action / Response → Experience

Experience records what actually happened, including context, route, decision,
action, result, success/failure, evidence and execution metadata where available.

Experience is NOT automatically knowledge and NOT automatically a skill.

============================================================
8. SELF-EVALUATION
============================================================

Experience → SelfEvaluator

SelfEvaluator separates:

    "something happened"

from:

    "JARVIS may learn something from it."

Possible outcomes include rejected/failed, insufficient evidence, or accepted learning signal.

============================================================
9. LEARNING COORDINATOR
============================================================

Self-Evaluation → LearningCoordinator

LearningCoordinator is the controlled dispatcher and separates:

    ├── Knowledge Path → KnowledgeBuilder
    └── Capability Path → SkillLearner

============================================================
10. KNOWLEDGE LEARNING PATH
============================================================

Experience → SelfEvaluator → LearningCoordinator → KnowledgeBuilder
→ Knowledge Candidate → Acceptance/Validation → Semantic Memory → Knowledge

Failed experiences MUST NOT automatically become knowledge.

============================================================
11. CAPABILITY / SKILL LEARNING PATH
============================================================

Experience → SelfEvaluator → LearningCoordinator → SkillLearner
→ Repeated Verified Success Detection → Skill Proposal → Validation
→ Explicit Approval → Activation → SkillRegistry → SkillExecutor

One successful experience cannot automatically create an executable skill.

============================================================
12. SKILL PROPOSAL BOUNDARY
============================================================

Skill Proposal MUST NOT auto-register or auto-activate.
Only explicit approval can cross the activation boundary.

============================================================
13. SKILL REGISTRY
============================================================

Only approved + activated capabilities become executable registered skills.

============================================================
14. SKILL EXECUTION FEEDBACK
============================================================

SkillRegistry → SkillExecutor → Action → Result → Experience → SelfEvaluator

Learned capabilities therefore participate in the same living cycle.

============================================================
15. EVOLUTION BOUNDARY
============================================================

Self-Evaluation / Learning → Evolution Boundary → Controlled Evolution

SelfEvaluation ≠ Evolution.
Learning ≠ Evolution.

Evolution requires an explicit controlled transition.

============================================================
18. FORBIDDEN SHORTCUTS
============================================================

Experience → Knowledge is forbidden.
Experience → SkillRegistry is forbidden.
SkillLearner → Auto Activation is forbidden.
SelfEvaluator → Auto Evolution is forbidden.
LLM → Direct unrestricted execution is forbidden.
Perception → Direct action is forbidden.
Router → Brain bypass is forbidden.

============================================================
19. SINGLE SOURCE OF TRUTH
============================================================

The lifecycle and boundaries above are canonical.
Individual modules and internal algorithms may evolve, but boundaries may not be
silently bypassed or rearranged.

20. IMPLEMENTATION RULE
============================================================

JARVIS is a controlled living loop:

PERCEIVE → UNDERSTAND → ROUTE → THINK → DECIDE → ACT → EXPERIENCE
→ EVALUATE → LEARN → EVOLVE → BECOME MORE CAPABLE → NEXT CYCLE

============================================================
21. ORGANISM IDENTITY — THREE LAYERS
============================================================

JARVIS identity is divided into three computational layers.

LAYER 1 — CORE IDENTITY (STABLE)

Contains organism invariants that are not learned from ordinary experience:

    ├── name
    ├── designation
    ├── creator/genesis metadata
    ├── fundamental purpose
    └── architectural/safety invariants

Core identity MUST NOT be silently rewritten by learning or LLM output.

LAYER 2 — ADAPTIVE SELF-MODEL (CHANGEABLE)

Contains validated current self-state such as:

    ├── known capabilities
    ├── known limitations
    ├── active goals
    ├── uncertainty/confidence
    ├── current strategies
    └── validated adaptations

Adaptive state may change only through authorized organism mechanisms.

LAYER 3 — AUTOBIOGRAPHICAL HISTORY

Contains identity-relevant history linked to actual evidence:

    ├── significant experiences
    ├── acquired capabilities
    ├── validated adaptations
    ├── important failures
    └── evidence/provenance for changes

History is not itself authority. It is evidence available to cognition,
evaluation and future adaptation.

============================================================
22. ORGANISM STATUS / SELF-OBSERVABILITY
============================================================

JARVIS status MUST distinguish:

    CODE PRESENT
    INTEGRATED
    RUNTIME ACTIVE
    RUNTIME VERIFIED

Attached-organ status alone MUST NOT be interpreted as proof of health or
successful operation.

The organism status surface should expose, where available:

    ├── layered identity
    ├── running state
    ├── uptime
    ├── last meaningful event
    ├── attached organ/type
    ├── declared organ responsibility
    ├── organ self-reported runtime state
    └── internal state snapshot

Status is observability, not a permission system and not a claim that the
organism is healthy merely because an object exists.

============================================================
23. ORGAN ROLE REGISTRY
============================================================

Organ responsibilities are declared in:

config/organism_roles.json

The runtime organism may expose these roles through its status surface.
Role metadata is descriptive architecture/configuration; execution authority
remains in the actual organ implementation and blueprint boundaries.
